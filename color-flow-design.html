Color Flow — Design reference v1.5

Reference, not gameplay UI. The section above is the simulated iPhone gameplay screen. This complete specification is deliberately placed below the screen so a future design or development session can recover the intended behavior. The HTML works offline.

Language and status

English only in all game UI, accessibility labels, JSON, level data, source code, names, and technical documentation. Current HTML is a single-level interactive visual demo, not a deployed level progression system. The numbered level catalog is a confirmed future feature, not yet wired to the demo.

Visible gameplay layout

Vertical order without explanatory labels in the gameplay screen: target grid, active bucket slots, and four independent columns of reserve paint tins. The current demo uses a 6×6 grid, three active slots, and blue, yellow, green, and purple paint. Reserve columns display the available front tin and up to two smaller, dimmer upcoming tins. Bucket/tin quantities are displayed as numbers; no color letters appear on the grid or containers.

Cell appearance and target previews

All target colors are defined from the start, but all cells begin unpainted. An unpainted cell has a dark neutral center and a thick colored border for its target color, with no colored center dot. A painted cell is filled with saturated target color and displays no check mark. Selecting an active bucket animates a bright, pulsing highlight on exactly the cells that bucket can paint in each eligible column. Tapping any highlighted cell starts a pour into its column. There are no arrows above the grid.

Deterministic bottom-to-top painting

Each column advances from its lowest unpainted cell toward the top. A bucket can pour into a column only when its color matches that next cell. One pour paints the maximum consecutive vertical run of the same color beginning at that cell, limited by the bucket's available units. One cell consumes one unit. No skipping, diagonal paths, obstacles, sources, flood filling, or randomness. After a partial pour, remaining paint stays in the active bucket; an exhausted bucket releases its slot. A target color can occur in disconnected positions.

Bucket slots and four paint queues

The current demo has three interchangeable active slots; future predefined levels specify their own bucketSlots. Exactly four independent paint queues are ordered left to right. Each queue is ordered front/top first: only its first remaining tin can be taken. Taking a tin advances that queue only. If an active bucket of the same color already exists, the tin's paint units are added to that bucket, even when all slots are full. Otherwise the tin occupies the first free slot. Multiple active buckets of the same color are prohibited. A tin cannot be taken when all slots are full and there is no same-color bucket. Tins can contain different positive quantities; the demo includes quantities of 1, 2, and 3.

Pour animation and interaction

On tapping a highlighted cell, the bucket appears immediately at the correctly aligned position above the selected column, without a visible sideways correction. It tilts and pours a single continuous stream from the actual rim/corner of the tilted bucket, centered horizontally over that column. Cells visibly fill one by one bottom to top. Do not display a floating dot, round droplet, or stray particle. All controls are disabled while the animation runs, and reduced-motion preferences are respected.

Win, loss, and demo status

Win: all target cells painted, all active buckets exhausted, and all four reserve queues empty. Immediate loss: all active bucket slots are full and no bucket can paint in any column. The native engine should also reject any other non-winning no-legal-move state so play cannot become stuck without feedback. The current demo constructs a solvable queue sequence programmatically; the confirmed future level system must instead use authored fixed JSON definitions.

Predefined numbered levels

Levels are permanently numbered 1, 2, 3, ... and labeled easy, medium, or hard. Each level defines exactly: grid, bucketSlots, and the contents and exact order of the four paintQueues; the ID and difficulty are metadata. Levels are fixed at runtime, not randomized. Queue order and tin quantities must be stored exactly as authored.

JSON structure: grid is an array of equal-length row strings, listed top to bottom; one uppercase color token is one cell, from left to right. paintQueues is an array containing four arrays of objects, ordered left to right. Each inner array lists tins in retrieval order (first item available first). Each tin object has color and positive integer paintUnits.

How level difficulty is determined

Three interacting factors matter: (1) how target colors are grouped vertically and distributed across columns; (2) the number of active bucket slots (fewer generally means harder); (3) whether the exact queue order conveniently exposes the next needed colors or forces careful retrieval, recharge, and slot-management decisions. A fragmented grid is not automatically hard if the queues are friendly, and a simple grid can be difficult with tight slots and adverse queue ordering. Judge choices, dependencies, plausible mistakes, and deadlock risk, not only pour count.

Easy: obvious, forgiving paths, mostly grouped colors, typically three slots. Medium: plan several moves ahead, some queue/slot dependencies, usually two or three slots. Hard: consequential retrieval order, convincing losing alternatives, often two slots and occasionally one only if carefully validated. Hard levels should be reasoned puzzles, not arbitrary traps.

Confirmed progression targets

All initial levels are easy. Medium levels become gradually more frequent; later, hard levels become increasingly common. Consecutive levels need not increase monotonically in difficulty: retain occasional relief levels. Level validation and iOS implementation

Before publication, every candidate level must pass: valid rectangular grid and color tokens; exactly four queues; positive tin units; supported slot count; exact equality between cell count and supplied paint units for each individual color; and an automated search proving at least one complete legal solution under the precise queue and slot rules. Paint totals alone do not prove solvability. Assess difficulty through solver statistics and human playtesting, then assign a permanent number and store the configuration. Preserve at least one winning move sequence as a regression test.

Suggested architecture: immutable LevelDefinition and PaintTin decoded with Swift Codable; mutable GameState; deterministic PuzzleEngine; LevelCatalog of authored files; LevelValidator and solver; SwiftUI GameView; and separate presentation-only PourAnimation. Use no backend for the MVP. The current prototype does not yet implement numbered-level navigation, variable slot counts, difficulty displays, or this complete catalog.
